# 手动亮度优先

2026-10-02，DisplayDJ 1.0.1。

## 用户行为

手动调节某块屏幕后，已存在的 Agent 会话在该屏的后续阶段、结束和超时中跳过亮度写入。其他屏幕和保活租约继续按会话配置处理。用户选中当前值也表示接管；手动写入失败后，旧会话仍不得覆盖用户意图。

接管入口覆盖菜单栏滑块、滚轮、快捷键和同步调节，主 CLI / HTTP 直接亮度写入，兼容 CLI，实际应用的亮度预设，以及显式 Gamma 设置或关闭。保存预设和 dry-run 不接管。系统设置、显示器实体按键和其他应用的修改尚不能触发此规则。

新会话可从当前亮度重新建立恢复点。重叠会话共享恢复点，最后一个仍有控制权的会话负责恢复。直接 `brightness set` 保留新的手动撤销点，显式 `brightness restore` / `panic` 才使用它；daemon 退出不撤销手动背光修改。Gamma 色表仍随驻留进程退出释放。

## 实现与接口

- `BrightnessCoordinator` 在硬件写入及确认期间持有跨进程锁；逐屏版本和恢复点所有权保存到共享状态文件。普通 CLI 无需启动 daemon。
- `BrightnessService` 从磁盘读取当前控制权，阻止旧进程缓存和旧快照恢复覆盖手动值；离线和失败恢复仍保留有效恢复点。
- `AgentSessionManager` 串行协调会话生命周期，在开始时捕获实际配置的各阶段目标；排除屏幕和未配置亮度的阶段不取得控制权，新接入屏幕不自动取得控制权。
- App、CLI 和服务必须使用同一状态目录和同一版本。旧状态可读取；缺少所有权的恢复点要求显式恢复或手动接管。损坏状态、锁冲突、运行中的旧 daemon 会阻止写入。
- CLI `agent begin/phase/end --json` 保留 `data.session`，同时返回 `brightness`、`keepAwake`、`warnings`。逐屏 `skippedReason` 说明未执行写入的原因，详见 [API.md](API.md)。
