# 仓库维护与发布标准

2026-10-16。适用于同仓库的 DisplayDJ Full 与 DisplayDJ Lite。

## 产品与维护范围

- Full 是已有的完整控制产品，沿用原有 bundle ID、命令行契约、配置和恢复数据。Lite 是当前围绕外屏断开/恢复进行验证的轻量入口，有独立 bundle ID 和恢复记录。
- 共享连接内核的修改必须评估两条线。Lite 专属布局、图标和打包变动不要求重做 Full 全部交互，也不自动触发 Full 升版。
- Full 已选交互稿是另行规划的本地设计，不随本次 Lite 提交发布；不把 Lite 的本轮改善写成 Full 已完成改版。两版共同规则见 [交互一致性契约](INTERACTION-CONTRACT.md)。
- 新能力先记录用户场景、现有替代方案和验收结果；不以维护为由增加输入切换、虚拟屏、预览、服务或收费系统。

## 版本、标签与支持口径

| 项目 | Full | Lite |
| --- | --- | --- |
| 当前版本源 | `Version.current`，当前 1.0.2 | `LiteIdentity.version`，当前 0.1.0 |
| 标签规则 | 保留 `v<version>` | 新发布使用 `lite-v<version>` |
| App 文件名 | `DisplayDJ.app` | `DisplayDJLite.app` |
| 资产前缀 | `displaydj-<version>-macos-<arch>` | `displaydj-lite-<version>-macos-<arch>` |
| 发布策略 | 功能/缺陷变化时独立递增 | 首次公开试用建议 0.1.0 预发布，注明设备与签名边界 |

版本数字不强制对齐。已发布版本的缺陷修复升 patch，新增兼容能力升 minor，破坏公开 CLI/API 契约需明确迁移方案与 major 决策。尚未公开的 Lite 0.1.0 可以继续收敛首发候选；公开后不覆盖同版本资产，以新版本发布修复。

仅文档、CI 和打包维护可随源码提交交付，不为此虚构新的 Full 功能版本。共享内核修复需要在各受影响产品的新版包中实际交付，不能只凭同仓库就声称旧下载已获得修复。

当前发行范围是已有证据支持的 arm64、macOS 13 部署目标；最低版本部署目标不等于最低版本实测。本地 ad-hoc 签名不等于 Developer ID 或 Apple 公证；硬件兼容按具体 Mac、系统、接线和显示器案例记录。维护者不预先承诺响应时限或全型号支持。

## 一套打包实现，两款独立 App

`package-product.py` 是唯一归档实现，`product_config.py` 定义产品身份与包内容。保留旧 shell 入口：

```bash
# 兼容旧用法：Full ZIP；默认仍为 Full。
bash scripts/package.sh
# Lite ZIP。
bash scripts/package.sh --product lite
# 一次构建，产出同一 App 的 ZIP、DMG 与各自 SHA-256。
bash scripts/package.sh --product lite --format all --output-dir /tmp/lite-release-candidate
# 原有 DMG 入口仍可用。
bash scripts/package-dmg.sh --product full
```

ZIP 为默认输出，DMG 保留为可选格式。不把两款 App 合并成一个安装包。已有同名包或校验文件时在构建前拒绝；失败留下的候选产物只用于排查，不上传。

打包器会从产品版本源构建 Release App，再自动执行包校验。当前允许有明确标注的 ad-hoc 候选包；单独执行校验时必须显式接受此签名状态：

```bash
python3 scripts/verify-package.py /tmp/lite-release-candidate/displaydj-lite-0.1.0-macos-arm64.zip \
  --product lite --expect-version 0.1.0 --allow-ad-hoc
```

校验覆盖产品 ID、版本、单一架构、确切可执行文件集合、图标、许可文件、签名、ZIP/DMG 中的逐文件字节、SHA-256。Full 额外核对两个 CLI 的版本。两个产品的 builder 都接受可选 `DISPLAYDJ_SIGN_IDENTITY`；Developer ID 分支尚需实际证书验证，签名成功仍不等于公证完成。

## 变更验证与发布门槛

| 改动 | 最小验证 |
| --- | --- |
| Lite UI / 生命周期 | Lite 连接与退出测试、App 构建和 bundle smoke；原生检查正常、取消、失败、长名称、键盘和浅深色适配 |
| 连接内核 | 相关内核与两款产品的行为回归；身份变化、镜像/最后一屏、重复点击、验证失败、恢复记录保留 |
| Full 亮度/快捷键 | 相应协调/呈现/按键测试及原生验证；必要时用已获授权的具体设备读回，保持 Gamma 显式选择 |
| 打包 | 两产品的包身份和字节校验；混错产品、篡改内容、版本不符、旧资产覆盖应拒绝 |
| 纯文档 | 链接、命令与当前脚本对应、格式检查；不重复运行无关硬件测试 |

CI 验证共享测试、Full 构建及 CLI smoke、Lite 构建及 bundle smoke。归档校验在本地候选包流程执行。CI 不执行真实显示连接事务，也不代表设备、Gatekeeper 或干净首装通过。

正式发布前逐项记录：

- [ ] 确定具体产品、版本、变更范围；只提交本次相关文件，保留其他未提交工作。
- [ ] 从确定 commit/tag 的独立源码构建；本地脏工作区产物只能叫候选包。
- [ ] 版本源、plist、tag、文件名、发布说明一致；同一批次 ZIP/DMG 复用同一 App。
- [ ] 完成对应产品的测试、包一致性与本机 UI 验证；硬件/安装缺口逐项注明。
- [ ] 显示连接变更仅针对明确授权目标；不能用模拟屏幕或按钮点击证明真实恢复。
- [ ] Lite 首次发布前补一轮经 Lite UI 的真实断开/恢复与恢复并退出；恢复失败先处理再扩大试用。
- [ ] 说明签名、公证、架构、已知设备限制、安装和恢复方法；不得把来源不明的失败诊断归咎硬件。
- [ ] 用户授权提交、推送及公开发布后执行相应步骤；不强推或改写历史。
- [ ] 发布后回读产品专属 Release 及下载字节/校验和，确认下载入口没有跳到另一产品；记录旧版本回滚办法。

本轮结论：Lite 0.1.0 已完成本机 Dell 的普通重连、恢复退出与主界面强制结束后的恢复验收，并经用户授权作为独立预发布版交付。Full 保持 1.0.2；已选正式版交互稿实现并验收后，再按实际改动决定其版本。现在不把两条线强行合成一次新版本发布。

## 问题反馈与回滚

Issue 先写产品与版本、macOS/架构、显示器及接线概况、预期和实际结果、是否恢复、可复现步骤。不要公开设备 UUID/序列号、访问 token、联系方式或完整原始日志。恢复失败优先处理，再处理分发阻塞和普通视觉缺陷；仅有下载计数不能确认为采用量。

安装候选前保留已发布旧包，退出正在使用的同产品实例并确认当前恢复状态；覆盖升级只操作对应 App，不清空用户数据、不重置其他应用权限。发生问题时停止新增连接操作，按原产品恢复入口处理，再回到已知版本；保留失败记录，不能通过删除恢复文件制造“已恢复”。

维护证据分为源码/测试、候选包、已安装实例、具体设备、CI、公开 Release、外部用户反馈。交付时说清本次达到了哪一层；未运行检查写明原因。

Lite 0.1.0 的恢复要求进一步收紧：正常退出必须恢复并核验，取消直接保留断开退出；新断开使用应用作用域，恢复连接提交到会话作用域，以处理旧断开基线。首发限制为有当前待恢复记录时不再断开另一台，完整边界和卸载步骤见 [LITE-RECOVERY.md](LITE-RECOVERY.md)。

Lite 0.1.0：断开前必须确认恢复子进程的父进程退出监视器就绪；不能仅依赖 `forAppOnly`。已确认旧编号被复用的未接入历史记录保留、禁止盲目启用，不阻塞当前屏幕操作和退出。实体证据见 [LITE-DEVICE-VERIFICATION.md](LITE-DEVICE-VERIFICATION.md)。
